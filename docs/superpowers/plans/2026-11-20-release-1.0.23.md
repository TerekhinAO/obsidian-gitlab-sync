# Release 1.0.23 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish version `1.0.23` so plugin updaters receive the corrected settings labels even after the stale `1.0.22` release assets.

**Architecture:** bump package, manifest, and version metadata together; make the release workflow idempotent by editing and clobbering assets when a release already exists; build and archive locally; publish a fresh tag; verify the exact public assets downloaded from GitHub.

**Tech Stack:** npm/pnpm lifecycle scripts, esbuild, GitHub Actions, `gh release`, shell verification.

**Spec:** Incident: `1.0.22` tag was force-moved, but existing GitHub Release assets were not replaced. Users updating received old `main.js` containing `(mobile only)` labels.

## Global Constraints

- Release version is exactly `1.0.23`.
- `package.json`, `manifest.json`, and `versions.json` must agree.
- Public Release assets must match the locally built bytes by SHA-256.
- Public `main.js` must not contain `Sync on app foreground (mobile only)` or `Sync on app background (mobile only)`.
- Release workflow must replace existing same-named assets on retried tags using `gh release upload --clobber`.
- Full verification must pass before tagging and publication.

## Review Focus

- A retried release tag must not leave stale assets.
- Version metadata must stay synchronized.
- The release archive and individual plugin files must contain version `1.0.23`.
- The release notes must reference `1.0.23`, not `1.0.22`.
- Verification must inspect the public downloaded assets, not only local build outputs.
